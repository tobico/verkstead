# 01. The `activity` world and block

## What to build

Give the `activity` Category its grammar and its WIT world, and have
`verkstead plugin check` and the loader read both. No Activity runs yet. This
task only makes one declarable, checkable and listable.

**The WIT.** `crates/server/wit/plugin.wit` holds an empty `world activity`
today, with bindings generated by `wasmtime::component::bindgen!` (wasmtime 50)
in `plugins/component.rs`. Fill it in.

- **Start facts**, handed in when the host starts the Activity:
  - the Repo, the branch and its base, and the Worktree's path;
  - the Companion Repos;
  - the roles' Pairings;
  - the Brief, and the handoff where there is one;
  - the Timeline so far, as data;
  - the Activity's **options** — what a Process will configure in stage 11. Stage 09's investigating rounds are this stage's follow-up rounds with different options;
  - the **sandbox path of each skill it declared**, so that the Activity can write its own prompt (Set 1803, Q5).
- **Events in.** These are the Nothing-else mark and a steer. Waiting on a session is a natural place for them to arrive: the wait returns *done*, *gone*, *stalled*, *steered* or *marked*. The exact shape is this task's to settle.
- **Host functions out.** The full list for this stage:
  - *launch a session*: `<pack>/<skill>`, a role, the prompt text, and the Done-signal evidence it expects. The evidence is `done.rs`'s `Evidence` generalised: landed, committed-since, nothing, nothing-else, investigated, plus how the session ends with its work;
  - *wait on it*;
  - *read the git facts* of the Worktree and of each Companion, read-only: commits past the base, the branch's name, whether anything is uncommitted;
  - *put a Timeline notice*;
  - *stop, with a reason* (Set 1803, Q6). This leaves the Conversation where it is, writes the stop notice, and closes any Set left open.

  **Not** *call the Forge* or *put a Question Set of Verkstead's own*. Each arrives in stage 09 with its first built-in caller (Set 1803, Q4).
- **The outcome back.** The Activity returns one of its declared Outcome words, or `steered`, which every Activity has. An Outcome never names a state.

**The block.** Add an `activity` entry to `provides:`. Its grammar goes in
`docs/plugins.md` beside `skills`, and is read in `plugins/manifest.rs` the way
`Walk::packs` reads a pack.

- A plugin may carry **several `activity` blocks, each naming its own component** (Set 1803, Q3). The built-in Activities are to be one plugin with a block per Activity, so a block carries:
  - its identifier;
  - its drawn name (e.g. *Follow-up rounds*);
  - its `component` (a `.wasm` inside the plugin's directory);
  - its `outcomes`;
  - the `skills` it launches, as `<pack>/<skill>`.
- The top-level `component:` stays for what is plugin-wide.
- **Refusals, by field:**
  - an Outcome repeated, or `steered` written out;
  - a skill not in `<pack>/<skill>` form;
  - a skill from a pack the plugin neither provides nor declares a **dependency** on, naming the skill (Set 1771, Q1);
  - an unknown key.

**The loader.**
- Each block's component is loaded and checked against the `activity` world's exports.
- A component lacking them, or importing what the host does not give, puts the plugin in **trouble**, with the sentence the Plugins page draws and `plugin check` prints. It is never a panic.
- The Plugins row, which today lists only the Category words, names the plugin's Activities by their drawn names. That is what lets stage 04 show *Follow-up rounds* under Built-in.

**Build.** `crates/server/build.rs` embeds one `<dir>.wasm` per plugin directory
today. It has to build and embed one component per `activity` block of a
built-in, so the per-block components ship in every binary the way the fixture's
does (`docs/development.md`, *Built-in plugins*).

Fixtures in the loader's tests are WAT made into components at test time
(`wat`, `wit-component`, `wit-parser` are dev-dependencies already). Use those
here rather than a wasm toolchain.

## Acceptance criteria

- [ ] A plugin providing an Activity, with a component exporting the world, passes `verkstead plugin check`, loads, and its row names the Activity.
- [ ] One whose component lacks the world's exports loads in trouble, its row and `plugin check` saying so.
- [ ] One naming a skill from a pack it neither provides nor depends on is refused, naming the skill and the field.
- [ ] `docs/plugins.md` documents the `activity` block and the world, and `build.rs` can embed a component per block of a built-in.
